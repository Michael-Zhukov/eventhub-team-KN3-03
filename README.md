# EventHub

Навчальний проєкт **EventHub** — портал продажу квитків на події.

Цей README призначений не тільки для запуску проєкту, а й для **покрокової перевірки роботи рев’юером**. Кожен крок містить команду та очікуваний результат.

### Ролі

**Backend** — підготовка backend-частини відповідно до визначеного API-контракту.

**Documentation** — документація проєкту та ADR.

## 2. Що реалізовано на Week 01

На цьому етапі використовується **design-first підхід**:

```text
OpenAPI contract
      ↓
openapi-typescript
      ↓
TypeScript types
      ↓
openapi-fetch
      ↓
Frontend
      ↓
Prism Mock API
```

Основні частини проєкту:

```text
apps/
├── api-gateway/       backend-заготовка
└── web/               React + TypeScript + Vite

packages/
├── config/            спільні конфігурації
└── contracts/         OpenAPI-контракт та генерація типів

docs/
└── adr/               архітектурні рішення
```

На Week 01 frontend працює з **Prism Mock Server**, а не з реальним API backend. Реалізація backend відповідно до цього контракту є наступним етапом.

Відкрийте окремий термінал у корені проєкту та виконайте:

```bash

```

---

# 9. Перевірка API

У новому терміналі виконайте:

```bash
curl http://127.0.0.1:4010/events
```

### Очікуваний результат

Сервер повертає HTTP `200` та JSON із полем `items`:

```json
{
  "items": [...]
}
```

У відповіді повинні бути події.

## 9.1. Перевірка параметра city

```bash
curl -G http://127.0.0.1:4010/events \
  --data-urlencode "city=Вінниця"
```

### Очікуваний результат

HTTP `200` та JSON із полем `items`.

## 9.2. Перевірка порожньої відповіді

```bash
curl -H "Prefer: example=empty" \
  http://127.0.0.1:4010/events
```

### Очікуваний результат

```json
{
  "items": [],
  "nextCursor": null
}
```

## 9.3. Перевірка помилки валідації

Передайте недопустимий `limit`:

```bash
curl -G http://127.0.0.1:4010/events \
  --data-urlencode "limit=999"
```

### Очікуваний результат

Сервер повертає HTTP `400` та тип відповіді `application/problem+json`.

Це перевіряє обмеження параметрів, описані в OpenAPI-контракті.

# 10. Запуск frontend

Не закриваючи Mock API, відкрийте ще один термінал та виконайте:

```bash
pnpm --filter web dev
```

### Очікуваний результат

Vite запускає frontend та показує локальну адресу, наприклад:

```text
http://localhost:5173/
```

Відкрийте адресу в браузері.

### Що повинно бути на сторінці

Повинні відображатися:

```text
EventHub
Квитки на події
```

та список подій.

Для події відображаються:

- назва;
- місто;
- дата та час;
- мінімальна ціна.

### Очікуваний результат

Якщо список подій відображається, frontend успішно отримує дані з Prism Mock API через типізований API-клієнт.

# 13. Перевірка інвалідації кешу після зміни OpenAPI

Відкрийте:

```text
packages/contracts/openapi.yaml
```

Зробіть невелику безпечну зміну, наприклад змініть опис існуючого поля.

Після збереження виконайте:

```bash
pnpm build
```

### Очікуваний результат

Зміна `openapi.yaml` повинна інвалідовати build пакета `contracts` та залежний build frontend.

Після проверки поверніть изменение `openapi.yaml` назад.

Це підтверджує ланцюжок залежностей:

```text
openapi.yaml
     ↓
contracts build
     ↓
web build
```

# 15. Перевірка `.env`

У репозиторії повинен бути файл:

```text
apps/web/.env.example
```

Він містить базовий URL mock API:

```text
VITE_API_URL=http://127.0.0.1:4010
```

Перевірити tracked env-файли можна командою:

```bash
git ls-files | grep env
```

### Очікуваний результат

У Git повинен бути `.env.example`, але не `.env.local`.

# 17. Фінальна перевірка

Після виконання окремих перевірок рев’юер повинен переконатися, що:

- [ ] `pnpm install` працює;
- [ ] OpenAPI-контракт знаходиться в `packages/contracts/openapi.yaml`;
- [ ] TypeScript-типи генеруються з OpenAPI;
- [ ] Prism Mock API запускається на порту `4010`;
- [ ] `GET /events` повертає `200`;
- [ ] помилковий `limit=999` повертає `400`;
- [ ] frontend запускається через `pnpm --filter web dev`;
- [ ] у frontend відображається список подій;
- [ ] TypeScript-перевірка проходить без помилок;
- [ ] `pnpm build` успішний;
- [ ] повторний build використовує Turbo cache;
- [ ] зміна `openapi.yaml` інвалідовує залежні build-задачі;
- [ ] generated-файли не знаходяться в Git;
- [ ] `.env.example` знаходиться в Git, `.env.local` — ні;
- [ ] ADR-001 містить негативні наслідки рішення.

Якщо всі пункти виконані, Week 01 можна вважати успішно перевіреним.

---

# 18. Важливо: backend

На Week 01 frontend спеціально працює через **Prism Mock Server**.

Реалізація реального API backend за тим самим OpenAPI-контрактом є наступним етапом проєкту.

Тому відсутність повноцінної реалізації backend на цьому етапі не є помилкою.
