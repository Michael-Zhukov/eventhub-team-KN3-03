# ADR-001: OpenAPI як єдине джерело правди для API-контракту

## Статус

Прийнято · 2026-09-13

## Контекст

На першому тижні EventHub потрібно було одночасно підготувати API-контракт і frontend, хоча реального backend ще немає.

Frontend має працювати з mock-сервером Prism, а в наступних тижнях backend має реалізувати той самий API. При цьому формати запитів, відповідей та помилок повинні бути однаковими для всіх частин системи.

Потрібно також уникнути ручного дублювання TypeScript-типів у frontend та ризику, що frontend і backend використовуватимуть різні версії контракту.

## Розглянуті варіанти

### Варіант A. OpenAPI як єдине джерело правди

* Плюси:

  * один контракт для frontend, mock-сервера та майбутнього backend;
  * TypeScript-типи генеруються автоматично;
  * API можна перевіряти ще до реалізації backend;
  * зміни контракту можна централізовано поширювати на споживачів.
* Мінуси:

  * OpenAPI-специфікацію потрібно постійно підтримувати в актуальному стані;
  * після змін контракту потрібно повторно генерувати типи;
  * помилка в специфікації може вплинути одразу на кілька частин проєкту.

### Варіант B. Ручне описання типів у frontend та окремий контракт backend

* Плюси:

  * frontend можна реалізовувати без окремого процесу генерації;
  * типи можна швидко змінювати без редагування OpenAPI.
* Мінуси:

  * типи та API-контракт дублюються;
  * можливі розбіжності між frontend і backend;
  * mock-сервер не має єдиного джерела даних про API;
  * зміни потрібно синхронізувати вручну в кількох місцях.

## Рішення

Використовуємо `packages/contracts/openapi.yaml` як єдине джерело правди для API-контракту. На його основі генеруємо TypeScript-типи через `openapi-typescript`, а frontend і Prism використовують цю саму специфікацію.

## Наслідки

**Позитивні**

* frontend, Prism та майбутній backend працюють за одним контрактом;
* TypeScript допомагає виявляти невідповідності API під час компіляції;
* frontend можна розробляти до готовності backend;
* типи API не потрібно дублювати вручну;
* зміни контракту проходять через одне центральне місце.

**Негативні й компроміси**

* команда повинна підтримувати `openapi.yaml` синхронізованим із реальною поведінкою API;
* зміна контракту може вимагати повторної генерації типів і перевірки залежних пакетів;
* з'являється додатковий інструмент і крок генерації під час розробки;
* помилкова специфікація може поширити неправильні типи на споживачів API.

**Що доведеться переглянути, якщо…**

* з'явиться потреба будувати API без OpenAPI або використовувати інший формат контракту;
* генерація типів перестане відповідати потребам frontend та backend;
* один контракт перестане бути достатнім для всіх споживачів API.
