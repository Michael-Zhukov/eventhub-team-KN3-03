# ADR-0005: Автентифікація через Argon2id, JWT та ротацію refresh-токенів

## Статус

Прийнято · 2026-10-20

*Рішення задокументовано після початкової реалізації в межах лабораторної №5.*

## Контекст

EventHub — портал продажу квитків на події. Для подальшої роботи із профілями користувачів, організаторами та захищеними операціями системі потрібна автентифікація.

Користувач повинен мати можливість зареєструватися за email і паролем, увійти до системи, переглянути власний профіль та завершити сеанс.

При цьому необхідно захистити паролі від розкриття у випадку витоку бази даних, обмежити час дії токенів доступу та запобігти повторному використанню викрадених refresh-токенів.

Оскільки frontend EventHub працює у браузері, окремо потрібно визначити спосіб зберігання токенів, щоб зменшити ризики, пов'язані з доступом JavaScript до довготривалих облікових даних.

## Розглянуті варіанти

### Варіант A. Довготривалий JWT у localStorage

Frontend зберігає JWT у `localStorage` і передає його у заголовку `Authorization` для кожного захищеного запиту.

- **Плюси:**
  - Проста реалізація на frontend і backend.
  - Не потрібно зберігати refresh-токени в базі даних.
  - Токен зберігається після перезавантаження сторінки.
- **Мінуси:**
  - JavaScript має доступ до токена, тому XSS-вразливість може призвести до його викрадення.
  - Довгий термін дії збільшує наслідки компрометації.
  - Негайне відкликання JWT ускладнене без додаткового серверного механізму.

### Варіант B. Короткоживучий JWT і refresh-токен у HttpOnly cookie

Backend видає короткоживучий access JWT і окремий випадковий refresh-токен. Access-токен зберігається у пам'яті frontend, а refresh-токен передається через HttpOnly cookie. На сервері зберігається лише хеш refresh-токена.

- **Плюси:**
  - Refresh-токен недоступний звичайному JavaScript через `HttpOnly`.
  - Короткий термін дії access JWT зменшує період його використання після компрометації.
  - Сервер може відкликати refresh-токени та виявляти повторне використання.
  - Після оновлення сторінки frontend може відновити авторизацію через refresh-cookie.
- **Мінуси:**
  - Потрібна таблиця refresh-токенів у базі даних.
  - Ротація ускладнює серверну логіку та потребує захисту від конкурентних запитів.
  - Cookie-автентифікація вимагає уважного налаштування CSRF-захисту, `SameSite`, `Secure` і шляхів cookie.

## Рішення

Обрано **варіант B**: короткоживучий JWT для доступу до API та випадковий refresh-токен у HttpOnly cookie з ротацією і серверним відкликанням.

Паролі користувачів зберігаються виключно у вигляді хешів Argon2id.

### Зберігання паролів

- Використовується алгоритм `Argon2id`.
- Параметри: `memoryCost = 65536`, `timeCost = 3`.
- Пароль має містити від 10 до 128 символів.
- Email нормалізується через `trim()` і `toLowerCase()`.
- Повторна реєстрація email повертає HTTP `409 Conflict`.
- Неправильний пароль і неіснуючий email повертають однакову відповідь HTTP `401 Unauthorized`.
- Для неіснуючого користувача виконується перевірка пароля проти допоміжного Argon2-хешу, щоб зменшити різницю в часі обробки запитів.

### Access-токен

- Використовується JWT із терміном дії **900 секунд**.
- JWT містить `sub` — ідентифікатор користувача та `role` — його роль.
- Підпис перевіряється на backend.
- Frontend зберігає access-токен лише в оперативній пам'яті, а не в `localStorage`.
- Захищений маршрут `GET /auth/me` вимагає заголовок `Authorization: Bearer <token>`.

### Refresh-токен

- Генерується з **32 криптографічно випадкових байтів**.
- Передається у форматі Base64URL.
- У PostgreSQL зберігається тільки SHA-256 хеш токена.
- Термін дії визначається налаштуванням `REFRESH_TTL_DAYS`, стандартно 30 днів.
- Cookie має параметри `HttpOnly`, `SameSite=Strict`, `Path=/auth`.
- У production також використовується `Secure`.

### Ротація та відкликання

- `POST /auth/refresh` перевіряє поточний refresh-токен.
- Використаний токен позначається через `usedAt`.
- Новий refresh-токен належить до тієї самої сім'ї `familyId`.
- Для позначення використання застосовується умовне оновлення запису через `updateMany` із перевіркою `usedAt = null` і `revokedAt = null`.
- При виявленні повторного використання відкликається вся сім'я токенів та записується попередження в журнал.
- `POST /auth/logout` відкликає сім'ю refresh-токенів і очищує cookie.
- Для конкурентних запитів необхідно додатково перевірити атомарність повного процесу ротації, включно зі створенням нового токена.

### Frontend

- Маршрути `/login` і `/me` реалізовано у вебзастосунку.
- Запити авторизації проходять через Vite proxy `/api/auth`.
- Proxy переписує шлях refresh-cookie з `/auth` на `/api/auth` для локальної розробки.
- Після перезавантаження сторінки access-токен відновлюється через refresh-cookie.
- Для одночасних запитів на оновлення access-токена використовується механізм single-flight.

## Наслідки

**Позитивні**

- Паролі не зберігаються у відкритому вигляді.
- Refresh-токени не зберігаються у відкритому вигляді в PostgreSQL.
- Access JWT має обмежений термін дії.
- Можна відкликати refresh-токени після виходу користувача.
- Повторне використання старого refresh-токена призводить до блокування його сім'ї.
- Користувач може залишатися авторизованим після оновлення сторінки без зберігання access-токена у `localStorage`.
- OpenAPI описує маршрути авторизації та їхні типи.

**Негативні й компроміси**

- Кожен вхід і оновлення refresh-токена потребують операцій із PostgreSQL.
- Потрібно очищувати прострочені та відкликані записи refresh-токенів.
- Помилки синхронізації конкурентних запитів можуть ускладнити ротацію.
- Access JWT залишається дійсним до завершення свого терміну, навіть якщо refresh-токени вже відкликані.
- Захист від XSS і CSRF усе одно потребує окремої уваги.
- Налаштування cookie відрізняються між локальною розробкою та production.

**Що доведеться переглянути, якщо…**

- З'явиться вимога негайно відкликати вже видані access JWT.
- Система перейде на декілька доменів або сторонні клієнтські застосунки.
- Зросте кількість одночасних запитів на оновлення токенів.
- З'являться вимоги до керування окремими пристроями та активними сеансами.
- Буде запроваджено зовнішнього постачальника ідентифікації через OAuth 2.0 або OpenID Connect.
